What you are asked to do

A UR5e traces the same commanded trajectory twice: once in Isaac Sim, once on real hardware carrying an instrumented sensor mount. The two do not agree. Your model is given the simulated sequence and must predict the real one.

Input, per run

{
  "run_id":      "v0p70_extended_stop_start_r02",
  "cell":        { "joint_vel": 0.70, "arm_config": "extended",
                   "traj_type": "stop_start" },
  "commanded":   [ {"type":"SCAN_L0_START","coords":[x,y,z,rx,ry,rz]}, ... ],
  "sim_sequence": {
     "t":       [0.000, 0.008, 0.016, ...],          // seconds, master clock
     "tcp_pos": [[x,y,z], ...],                      // metres, robot base frame
     "tcp_rot": [[rx,ry,rz], ...],                   // rotation vector, radians
     "imu":     { "ind0": { "quat": [[w,x,y,z],...],
                            "gyro": [[x,y,z],...],   // rad/s
                            "accel":[[x,y,z],...] }} // m/s^2
  }
}

Output, per run

{"run_id": "...", "mode": "absolute",
 "t": [...], "tcp_pos": [[x,y,z], ...], "tcp_rot": [[rx,ry,rz], ...]}

One JSON object per line. mode is "absolute" (you predict the real sequence) or "correction" (you predict the delta and we add it to the simulation). Either is fine; the harness states which you used. Timestamps must match the simulated sequence you were given.

How it is scored

GCR = 1 - err(your prediction, real) / err(simulation, real)

Reported at the median and at the 95th percentile, per condition cell and overall. The p95 figure is the headline. Also reported: geodesic orientation error on SO(3), and a Wasserstein distance between the predicted and real error distributions, which is what separates matching the mean from matching the behaviour.

The held-out set

Whole condition cells are held back, not random samples. Interpolating inside a condition you have seen is easy; the unsolved problem is generalising across conditions — to an elbow velocity or an arm configuration you were never shown. The published example set spans the range; the scoring set contains cells you have not seen.

Why these modalities

Orientation, angular rate, acceleration and position. Nothing exotic. They are the quantities that are cheap to ground-truth on real hardware and faithful to generate in simulation, which is the only combination that produces a gap you can trust rather than a gap that is really a modelling artefact. An eddy-current or ultrasonic response would be a richer signal and an unfalsifiable one: nobody can simulate it accurately enough for the difference to mean anything.

Tail ratio is p95 divided by median. A cell with a high tail ratio contains the rare, badly behaved samples — the long-tail cases that a model trained on means will miss and that a safety-critical application cannot afford to.

What this rig can and cannot resolve

Every number on this site is reported against the measurement floor of the apparatus that produced it. A benchmark that does not publish its own floor will be challenged on exactly that point, so the answer is here rather than in a reviewer's email.

If the gap falls below the floor

Then the honest result is that the gap is below what this rig can resolve, and that is itself a publishable finding — provided it is stated rather than disguised. Cells in that position are flagged in the leaderboard rather than silently scored.

Running the harness

The scoring code is the same code that produced this page. You can run it against the published example set before you submit, so there are no surprises in the interface.

# see the whole pipeline on synthetic data with a known injected gap
python -m sonair_benchmark demo --out demo/

# score your own predictions against the example set
python -m sonair_benchmark score \
    --real data/real --sim data/sim \
    --budget calib/budget.json --plan campaign/plan.json \
    --submission my_model.jsonl --name "My model" \
    --out site/leaderboard.json

The two baselines your model has to beat

  1. Identity — hand back the simulation unchanged. Scores 0 by construction. This is the denominator of every GCR.
  2. Constant offset — fit one global XYZ offset on the example set and apply it everywhere. It is the dumbest thing that could possibly work. A model that does not beat it has not demonstrated anything, and the board will say so.

Both are computed through the same code path as every submission. A benchmark whose baseline is computed separately will eventually disagree with itself.

Submitting

Send the JSONL prediction file and a one-paragraph description of the method. Scoring is run against held-out cells that are not published. We report your per-cell scores back to you in full, including the cells you did worst on — a score without its failure modes is not useful to anyone.
