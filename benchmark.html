The benchmark, live from the cell

While the cell runs, the reference simulation S0 — and any candidate model loaded beside it — is driven by the real controller's own commanded joints, packet by packet. Every recorded run is scored the moment it ends, by the same rules as the leaderboard: tool-position error, median and 95th percentile, and GCR = 1 − err(candidate) / err(S0). Two ways to close the gap

Both tracks start from the same thing: the joint trajectory the robot's own controller commanded, target_q, at 125 Hz. The real arm executed it; the reference simulator (S0) executed it. Everything that separates the two is the sim-to-real gap.

Track A

Make the simulator right

Given the commanded joints, simulate the arm so that it moves the way the real one did.

How it is scored

GCR = 1 - err(entry, real) / err(S0, real)

Per-sample tool-position error, reported at the median and at the 95th percentile, per condition cell and overall; the p95 figure is the headline. Also reported: geodesic orientation error on SO(3), and how far the entry moves the whole error distribution towards zero (a Wasserstein distance), which separates matching the average from matching the behaviour. Both tracks are scored by the same code against the same reference, so their numbers are directly comparable.

Track C — bring your own robot: the acquisition platform, protocol and harness are open, so a second lab can record the same campaign on its own arm and be scored on the same scale. Planned for a later round.

Why whole cells are held back

Interpolating within an operating condition you have seen is easy. The open problem is generalising across conditions — to an elbow speed or an arm configuration you were never shown. So whole condition cells are held back, chosen once with a fixed seed before any data existed, spread across the speeds. For them we release what a submission needs as input — the commanded trajectory and the S0 simulation — and keep the real runs.

One run, one file

JSON Lines: a manifest on the first line, one sample per line after it. A run that was interrupted is still a valid run up to the point it stopped.

{"_manifest": {"run_id": "v0p60_extended_stop_start_r03", "side": "real",
               "experiment": "E2", "joint_vel": 0.6, "arm_config": "extended",
               "traj_type": "stop_start", "repeat_idx": 3,
               "carrier_mass_kg": 0.19, "carrier_com_m": [-0.012, -0.037, 0.008],
               "sample_rate_hz": 125.0, "calib_version": "...", "notes": "..."}}
{"t": 12.336, "target_q": [...6], "target_qd": [...6], "target_moment": [...6],
 "q": [...6], "qd": [...6], "tcp_pos": [x,y,z], "tcp_rot": [rx,ry,rz],
 "speed_scaling": 1.0, "aux": {"controller_t": 20040.929},
 "imu": {"ind0": {"quat": [w,x,y,z], "gyro": [...3], "accel": [...3]}}}

target_q is what a simulator must be given; feeding it the measured q would reproduce the answer and measure nothing. aux.controller_t is the controller's own clock, unaffected by the recording PC. Units: metres, radians, seconds, newton-metres, m/s².

Checking a download

Every release carries a manifest.json with its versions and a SHA-256 for every file. python -m sonair_benchmark verify-release <folder> checks the copy you have against it — and confirms that no held-out real data is in it.

How the recording is kept honest

  • Every run is read back as it closes; one that does not reach its labelled speed, holds stale robot data, or loses the inertial sensor is re-recorded, not kept.
  • Rehearsals on the simulated cell (URSim controller, MuJoCo arm) are labelled as such in their own manifests and never enter the dataset.
  • The motion protocol is versioned: a run recorded under a superseded protocol is kept as history and recorded again.

Tail ratio is p95 divided by median. A cell with a high tail ratio holds the rare, badly behaved samples — the cases a model trained on averages will miss and a safety-critical application cannot afford to.

What this rig can and cannot resolve

Every number on this site is reported against the measurement floor of the apparatus that produced it. Two repeats of the same cell on the real arm differ by 0.04 mrad at the elbow (RMS, Session 1) — the real-against-real spread no simulator can be asked to beat.

Rows combine in root-sum-square, not as an arithmetic sum: they are independent measurements, and summing them would overstate the floor and let a real gap be dismissed as noise.

If the gap falls below the floor

Then the honest result is that the gap is below what this rig can resolve, and that is itself a finding — provided it is stated rather than disguised. Cells in that position are flagged on the board rather than silently scored.

Taking part

The scoring code is the code that produced this page. Run it on the published cells before you submit and there are no surprises in the interface.

Track A  A MuJoCo model

The contract is small, and checked when the model loads:

  • the six UR joints by their UR names, in UR order (shoulder_pan_joint … wrist_3_joint);
  • six actuators whose ctrl is the commanded joint position;
  • a site named attachment_site at the tool flange.

Everything else — masses, friction, armature, gains, solver settings — is yours. The sensors are ours, wrapped around your model, so every model is measured the same way at the same point.

# simulate every run through your model, exactly as S0 is
python -m sonair_benchmark simulate --model my_ur5e/ur5e.xml \
    --real data/real --out results/my_model

# score it
python -m sonair_benchmark score --real data/real --sim data/sim_s0 \
    --budget calib/budget.json --plan campaign/plan.json \
    --track-a "My model=results/my_model" --out site/leaderboard.json

Another engine? Generate a simulated run per real run from its target_q, in the run-file format above with "side": "sim", and pass the folder to --track-a.

Track B  A prediction file

{"run_id": "v0p60_extended_stop_start_r03", "mode": "absolute",
 "t": [...], "tcp_pos": [[x,y,z], ...], "tcp_rot": [[rx,ry,rz], ...]}

One object per line. mode is "absolute" (you predict the real run) or "correction" (you predict the difference and we add it to S0); timestamps are those of the S0 simulation you were given.

python -m sonair_benchmark score --real data/real --sim data/sim_s0 \
    --budget calib/budget.json --plan campaign/plan.json \
    --track-b "My model=my_predictions.jsonl" --out site/leaderboard.json

Try the whole chain first

python -m sonair_benchmark demo --out demo/    # synthetic data with a known, injected gap

Submitting

Send the model folder (Track A) or the prediction file (Track B), with a paragraph on the method. It is scored on the held-out cells, which are not published. You get your per-cell scores back in full, including the cells you did worst on — a score without its failure modes is no use to anyone.
